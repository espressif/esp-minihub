Deploy Index
============

:link_to_translation:`zh_CN:[中文]`

The PC deploy root (``MINIHUB_PLUGINS_DEPLOY_DIR``, default
``~/workspace/minihub_store``) holds plugins, firmware, assets, and the
web console. ``python3 tools/store_server.py --deploy ROOT`` serves that
tree on port 8080 (override with ``--port``). ``store_server.py`` and the public
portal implement the same HTTP layout for plugins, firmware, assets, and web
bundles under the deploy root. ``https://minihub.espressif.com`` — the compiled-in
default for ``MINIHUB_STORE_URL`` — is a second implementation of the same
endpoints, so a download URL read from a response is used as it stands: a store
may address the package by version, unlike the folder it was imported from.

Plugins
-------

Every published module is one ``.mhub``. JSON and JS go under
``Stores/Common/<id>/``. A native or hybrid module is not a store package:
``store_buckets_for_module()`` gives it no bucket and a leftover folder is
deleted, so a store tree holds JSON/JS only. ``catalog.json`` is a single object
written next to the ``.mhub`` when packed (``tools/sync_store_catalog.py``).

.. code-block:: text

   ROOT/Stores/Common/ID/ID.mhub
   ROOT/Stores/Common/ID/catalog.json

``tools/sync_store_catalog.py`` writes ``url`` as the folder path, for example
``/files/Stores/Common/ID/ID.mhub``. ``GET /api/catalog`` walks ``Stores/Common``
and returns the compatible plugins (see below). The Hub store client downloads
the ``url`` inside that response and never rebuilds it: the public portal serves
the same package from an address that carries the version, for example
``/files/Stores/Common/ID/releases/1.0.0/ID.mhub``.

A plugin catalog entry looks like (generated by
``tools/sync_store_catalog.py`` from the built ``.mhub``):

.. code-block:: JSON

   {
     "type": "module", "id": "foo", "name": "Foo", "version": "1.0.0",
     "targets": ["any"], "url": "/files/Stores/Common/foo/foo.mhub",
     "size": 1234, "sha256": "0123abcd..."
   }

What gates a plugin: ``targets`` (``?chip=``) on the server and again on the
device. The catalog request also sends ``caps=``, the capabilities this Hub
currently has enabled. The server omits a plugin whose ``requires`` is not
covered. An empty or omitted ``requires`` stays listed. An installed plugin
whose capability was turned off is left installed, is not started on the next
boot, and the store labels it as not supported by this firmware.
The server's ``abi`` check runs only when the request carries both
``abi_version`` and ``abi_total_hash``, which the Hub does not send; JS and
config-only entries carry no ``abi`` block and are always compatible. What does
run on the Hub is local — it verifies the package's host symbols before
installing, and the loader verifies ``abi_version`` / ``core_api_min`` /
``core_api_max`` before loading.

Catalog entry fields
---------------------

``catalog.json`` is one object per module. Fields:

* ``type`` — always ``"module"``.
* ``id`` — module id (matches the folder and ``.mhub`` name).
* ``name`` — display name; defaults to ``id``.
* ``version`` — module version from ``module.json``; defaults to ``1.0.0``.
* ``vendor`` — vendor string from ``module.json``; empty if omitted.
* ``description`` — ``description`` from ``module.json``.
* ``adapter`` — the ``adapters.json`` key Host creates/enables; derived from
  ``adapter`` or ``inject.adapter``. When both are absent, the first
  ``requires`` entry is used.
* ``requires`` — capabilities this plugin needs, from ``Zigbee``, ``BLE``,
  ``BLE_mesh``, ``Thread_Matter``, ``Matter``, ``MQTT_Broker``, and
  ``Modbus``. ``BLE`` and ``BLE_mesh`` both track the ``ble_mesh`` adapter
  (``host.ble`` / passive scan needs the same stack). Empty means none. A
  listed capability must be compiled in and enabled. The store omits the
  plugin from the available list otherwise.
  Already installed plugins stay listed and are marked not supported by this
  firmware.
* ``url`` — the download path. The local tree uses
  ``/files/Stores/<bucket>/<id>/<id>.mhub``; a store may version it.
* ``targets`` — list of chip folder names (e.g. ``["esp32s31"]`` or
  ``["any"]``); the chip filter for ``?chip=``. ``ALL`` and ``*`` are the
  same wildcard as ``any``.
* ``runtime`` — ``"pack"`` (config-only JSON) or ``"js"`` (JS). ``"hybrid"`` and
  ``"native"`` describe a native module and are never published.
* ``config_only`` — ``true`` only for config-only JSON packs.
* ``size`` — byte length of the ``.mhub``.
* ``sha256`` — 64-digit hex digest of the ``.mhub``.
* ``host_api`` — JS and hybrid only: from ``module.json``, ``0`` when omitted.
* ``abi`` — native and hybrid only: ``abi_version`` plus ``symbols``, the hashes
  of the host symbols the package links. A Hub store tree has no such entry,
  because it publishes no native or hybrid package.

``ui`` and ``capabilities`` are not catalog fields. They stay in the package
``meta.json``. After install the console reads them from ``GET /api/modules``.

Device query parameters
-----------------------

Every device request — ``/api/catalog``, ``/api/firmware``, ``/api/assets``,
``/api/web`` and each ``/files/…`` download — carries the same query
parameters:

* ``mac`` — lowercase, colon-separated. Used only for the server-side
  overrides authorization; a request without it is still served, and only the
  access log notes its absence.
* ``chip`` — the device's lowercase ``CONFIG_IDF_TARGET``. The server drops
  entries whose ``targets`` name another chip; a request without ``chip`` is
  not filtered.
* ``board`` — the product's ``CONFIG_MINIHUB_BOARD`` (for example
  ``ESP32-S31-Function-Coreboard-1``). Optional. When present, firmware is
  offered only if that version folder's ``boards.txt`` lists the board (or
  ``*`` / ``ALL``). A version without ``boards.txt`` is chip-wide only for
  requests that omit ``board``. Independent of esp_board_manager's hardware
  board id.
* ``cur_version`` — the firmware version the device currently runs. Optional.

The server filters by ``chip`` and ``board``; the device filters the result
again locally as defense in depth.

Fetch protocol (``/api/catalog``)
---------------------------------

The server walks ``Stores/Common`` and returns the latest build per plugin id;
with zero matches ``status`` is ``no_plugin_for_version`` and ``plugins`` is
empty.

``firmware_upgrade.version`` is the highest MiniHub firmware directory name
for that chip that matches ``board`` (when sent). ``available`` is true when
that directory contains a ``.bin``. ``firmware_url`` points at the file. When
``cur_version`` is supplied, ``newer`` is true if a published version is
greater than it. The device does not read this field when it installs
firmware; that decision is ``GET /api/firmware`` below.

Request examples
----------------

The store listens on ``http://0.0.0.0:8080`` by default, so a device on the LAN
can reach it (override the address with ``--host``).

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/catalog?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&board=ESP32-S31-Function-Coreboard-1&cur_version=0.1.0"

HTTP 200. Matching plugins, plus the highest published firmware version:

.. code-block:: JSON

   {
     "status": "ok",
     "plugins": [
       {
         "id": "foo",
         "name": "Foo",
         "version": "1.0.0",
         "targets": ["esp32s31"],
         "url": "/files/Stores/Common/foo/foo.mhub",
         "size": 1234,
         "sha256": "ab93bfdd952f04b5c47b7ef1733e3774aaa1b852a453f6ad7b53437a01647ffe"
         }
     ],
     "firmware_upgrade": {
       "available": true,
       "version": "0.1.0",
       "firmware_url": "/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin"
     }
   }

Download the package from the returned ``url``:

.. code-block:: bash

   curl -s -o foo.mhub "http://127.0.0.1:8080/files/Stores/Common/foo/foo.mhub?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31"

Firmware
--------

One folder per chip and version. The folder has no JSON file:

.. code-block:: text

   ROOT/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin
   ROOT/Firmwares/esp32s31/0.1.0/release_notes.txt
   ROOT/Firmwares/esp32s31/0.1.0/boards.txt
   ROOT/Firmwares/esp32s31/0.1.0/bootloader.bin
   ROOT/Firmwares/esp32s31/0.1.0/partition-table.bin
   ROOT/Firmwares/esp32s31/0.1.0/merged.bin
   ROOT/Firmwares/esp32s31/0.1.0/minihub.elf
   ROOT/Firmwares/esp32s31/0.1.0/flash_command.txt

``boards.txt`` lists ``CONFIG_MINIHUB_BOARD`` ids (one per line), or ``*`` /
``ALL``. Devices that send ``board=`` only see versions that list them.
``python3 tools/publish_firmware.py --board …`` copies the application
``.bin``, the note, and ``boards.txt``. ``python3 tools/gen_flash_binaries.py``
adds the rest of the flash set to that same folder. Chip directory names are
lowercase.

``GET /api/firmware`` returns a JSON array listing each application image the
requested ``chip`` can run (the device filters the array again by ``targets``):

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/firmware?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s -o minihub.bin "http://127.0.0.1:8080/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin?mac=aa:bb:cc:dd:ee:ff&cur_version=0.1.0"

.. code-block:: JSON

   [
     {
       "id": "esp32s31-0.1.0",
       "name": "minihub-esp32s31-0.1.0",
       "version": "0.1.0",
       "chip": "esp32s31",
       "targets": ["esp32s31"],
       "sha256": "0123abcd...",
       "size": 1234,
       "release_note": "first cut",
       "url": "/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin"
     }
   ]

* ``version`` — the version directory name.
* ``chip`` and ``targets`` — the chip directory name.
* ``sha256`` — the 64-digit hex digest of the ``.bin``.
* ``size`` — the byte length.
* ``release_note`` — the text of ``release_notes.txt`` in the same directory.
* ``url`` — a path inside the deploy root. When one version directory holds
  several application ``.bin`` files, ``id`` also includes the file name.

On the device, ``minihub_update_check()`` and ``minihub_update_apply()``:

1. Request the array above with ``mac``, ``chip``, ``board``, and ``cur_version``.
2. Keep the highest version whose ``targets`` match the local chip name
   (case-insensitive). A leading ``v`` on a version is ignored in the compare.
3. Download when that version is higher than ``CONFIG_MINIHUB_VERSION`` (or
   the application description version when that option is empty). The same
   version is downloaded again when its ``size`` or ``sha256`` differs from
   the last download record.
4. ``minihub_ota_start_url()`` opens ``url`` and attaches ``mac``, ``chip``,
   ``board``, and ``cur_version``. The firmware stream is **not** compared against ``sha256``:
   the digest is only metadata used in step 3, so a re-published build under the
   same version number is re-fetched. The stream is staged on external LittleFS
   media, and Vibe Mode copies it into ``ota_0``. ``esp_ota_end()`` checks the
   header and sequence checksum at the end of that copy; matching
   ``app_elf_sha256`` lets Vibe Mode skip an unchanged image. See
   :doc:`../ota`.

   Only the asset and web downloads verify ``sha256`` before replacing a file.

Assets and web
--------------

``python3 tools/gen_deploy_index.py --deploy ROOT`` emits the device-type
registry from ``model/*.csv`` and ``images/*`` in the device-widget source:

* ``Assets/device_widgets.json`` — per ``device_id``: ``icon`` plus each
  parameter's ``icon`` and ``meta``.
* ``Assets/parameters.json`` — the global parameter registry (``icon`` /
  ``meta``) keyed by parameter name.

No per-parameter stylesheet is published. The ``css`` column of
``parameters.csv`` holds a **class name**, not CSS text: the console hands it to
``dwCssClass()`` and the rules themselves live in the bundled
``device_widgets.css``, which arrives inline with ``GET /api/device_widgets``.
A stylesheet can still be pushed by hand through the dev panel
(``PUT /api/dev/assets/styles/...``).

The web and asset manifests (schema ``minihub.deploy.index/1``) are served
dynamically by ``store_server.py`` as ``GET /api/web`` and ``GET /api/assets``:
they are built from ``Webs/<version>/`` and ``Assets/`` at request time, so no
static ``index.json`` is written (mirroring ``GET /api/firmware``).

``--only assets`` rebuilds only the device-type registry after a single icon file
is dropped in — no firmware or plugin rebuild required. ``--sync-source``
copies ``model/`` and ``images/`` from the device-widget component into the
deploy root first.

.. code-block:: text

   ROOT/Assets/device_widgets.json
   ROOT/Assets/parameters.json
   ROOT/Assets/model/*.csv
   ROOT/Assets/images/{devices,parameters}/*.svg
   ROOT/Webs/<version>/...   (manifest served at GET /api/web)

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/assets?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s "http://127.0.0.1:8080/api/assets/device/light?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s "http://127.0.0.1:8080/api/web?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"

On-demand device-type assets:

* ``GET /api/assets/device/<device_id>`` — that device's icon + each
  parameter's icon and metadata; 404 when unknown.
* ``GET /api/assets/parameter/<param>`` — the generic parameter entry.
* ``GET /files/...`` — serves the tree and rejects ``..`` / escape.

On the device, ``components/minihub_update/update_assets.c`` does **not** ask for
metadata first: the avatar is ``<type>.svg`` by convention, so it fetches
``GET /files/Assets/images/devices/<type>.svg`` directly and keeps it at
``/data/images/devices/<type>.svg``. That is deliberate — the metadata route is
driven by ``model/devices.csv``, so it 404s for a plugin-owned type, and such a
type could never have got an icon. A file already on the device is left alone, so
the hourly pass costs nothing once a type has been fetched, and repainting the
artwork on the server does not reach devices that already hold the file.
Parameter icons are not fetched.

``GET /files/...`` maps onto the deploy root and rejects a path that
contains ``..`` or escapes the root.

On the device, ``minihub_update_check()`` and ``minihub_update_apply()``
(``components/minihub_update``) read ``/api/firmware``,
``/api/assets``, and ``/api/web``. Firmware
calls ``minihub_ota_start_url()``. ``devices.csv`` and
``parameters.csv`` go through ``minihub_device_widget_put_model()`` into
``/data/config/model``. Other model files land in that directory.
Images land in ``/data/images``. Web files land in ``/data/web``.
Downloads are hashed while they are written; a mismatch is discarded.
