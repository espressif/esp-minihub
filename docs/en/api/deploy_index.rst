Deploy Index
============

:link_to_translation:`zh_CN:[中文]`

The PC deploy root (``MINIHUB_PLUGINS_DEPLOY_DIR``, default
``~/workspace/minihub_store``) holds plugins, firmware, assets, and the
web console. ``python3 tools/store_server.py --deploy ROOT`` serves that
tree on port 8080 (``MINIHUB_STORE_PORT``). The full contract (every index
format and the ``/api/*`` protocol) is the single source
of truth in ``minihub_website_internal/README.txt`` at the repository root.

Plugins
-------

Every module is published as one ``.mhub``. L1/L2 go under
``Stores/Common/<id>/``. ``catalog.json`` is a single object
written next to the ``.mhub`` when packed (``tools/sync_store_catalog.py``).

.. code-block:: text

   ROOT/Stores/Common/ID/ID.mhub
   ROOT/Stores/Common/ID/catalog.json

The object includes ``size``, ``sha256``, ``url``, and ``targets``. ``url``
matches the folder, for example ``/files/Stores/Common/ID/ID.mhub``.
``GET /api/catalog`` walks ``Stores/Common`` and
returns the compatible plugins (see below). The Hub store client downloads
the ``url`` inside that response.

A plugin catalog entry looks like (generated by
``tools/sync_store_catalog.py`` from the built ``.mhub``):

.. code-block:: json

   {
     "type": "module", "id": "foo", "name": "Foo", "version": "1.0.0",
     "targets": ["ALL"], "url": "/files/Stores/Common/foo/foo.mhub",
     "size": 1234, "sha256": "0123abcd..."
   }

``sha256`` is the 64-digit hex digest of the ``.mhub``. Plugins are
compatible as built: the server filters only by ``targets`` (``?chip=``)
and the device filters again locally as defense in depth.

Catalog entry fields
---------------------

``catalog.json`` is one object per module. Fields:

* ``type`` — always ``"module"``.
* ``id`` — module id (matches the folder and ``.mhub`` name).
* ``name`` — display name; defaults to ``id``.
* ``version`` — module version from ``module.json``; defaults to ``1.0.0``.
* ``vendor`` — vendor string from ``module.json``; empty if omitted.
* ``description`` — ``description`` from ``module.json``.
* ``adapter`` — the ``adapters.json`` key Host creates/enables; derived from
  ``adapter``, ``inject.adapter``, or the first ``requires`` entry.
* ``url`` — ``/files/Stores/<bucket>/<id>/<id>.mhub``; the download path.
* ``targets`` — list of chip folder names (e.g. ``["esp32s31"]`` or
  ``["ALL"]``); the chip filter for ``?chip=``.
* ``runtime`` — ``"pack"`` (config-only L1) or ``"js"`` (L2).
* ``config_only`` — ``true`` only for config-only L1 packs.
* ``size`` — byte length of the ``.mhub``.
* ``sha256`` — 64-digit hex digest of the ``.mhub``.

``ui`` and ``capabilities`` are not catalog fields. They live in ``meta.json``
inside the ``.mhub``.

Device requests add ``mac`` (lowercase, colon-separated), ``chip``
(lowercase, the device's ``CONFIG_IDF_TARGET``), and ``cur_version`` (the
firmware version the device is currently running) on the plugin catalog,
``/api/firmware``, ``/api/assets``, and ``/api/web``; the server filters the
catalog and firmware by chip, and the device filters again locally. Each plugin
download, the firmware ``.bin``, each asset file, and each web file also
carries ``mac``, ``chip``, and ``cur_version``.

Fetch protocol (``/api/catalog``)
---------------------------------

The query carries ``mac`` (lowercase, colon-separated), ``chip``
(lowercase, the device's ``CONFIG_IDF_TARGET``), and may carry
``cur_version`` (the firmware version the device is currently running).
The server filters catalog entries by ``chip`` and the device filters again
locally as defense in depth.

* ``mac`` — used only for per-device authorization (overrides).
* ``chip`` — the device's chip; the server drops entries whose ``targets``
  name another chip.
* ``cur_version`` — optional. The server uses it to report whether a newer
  firmware is published (see ``firmware_upgrade.newer``).

The server walks ``Stores/Common`` and returns the latest build per plugin
id. With zero matches ``status`` is ``no_plugin_for_version`` and
``plugins`` is empty.

``firmware_upgrade.version`` is the highest MiniHub firmware directory name
for that chip. ``available`` is true when that directory contains a ``.bin``.
``firmware_url`` points at the file. When ``cur_version`` is supplied,
``newer`` is true if a published version is greater than it. The device does
not read this field when it installs firmware; that decision is
``GET /api/firmware`` below.

Request examples
----------------

The store listens on ``http://127.0.0.1:8080`` by default.

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/catalog?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"

HTTP 200. Matching plugins, plus the highest published firmware version:

.. code-block:: json

   {
     "status": "ok",
     "plugins": [
       {
         "id": "foo",
         "name": "Foo",
         "version": "1.0.0",
         "targets": ["esp32s31"],
         "url": "/files/Stores/Common/foo/foo.mhub",
         "size": 1234,
         "sha256": "ab93bfdd952f04b5c47b7ef1733e3774aaa1b852a453f6ad7b53437a01647ffe"
         }
     ],
     "firmware_upgrade": {
       "available": true,
       "version": "0.1.0",
       "firmware_url": "/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin"
     }
   }

The package ``sha256`` is 64 hex digits. Download the package from the
returned ``url``:

.. code-block:: bash

   curl -s -o foo.mhub "http://127.0.0.1:8080/files/Stores/Common/foo/foo.mhub?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31"

Firmware
--------

One folder per chip and version. The folder has no JSON file:

.. code-block:: text

   ROOT/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin
   ROOT/Firmwares/esp32s31/0.1.0/release_notes.txt
   ROOT/Firmwares/esp32s31/0.1.0/bootloader.bin
   ROOT/Firmwares/esp32s31/0.1.0/partition-table.bin
   ROOT/Firmwares/esp32s31/0.1.0/merged.bin
   ROOT/Firmwares/esp32s31/0.1.0/minihub.elf
   ROOT/Firmwares/esp32s31/0.1.0/flash_command.txt

``python3 tools/publish_firmware.py`` copies the application ``.bin`` and the
note. ``python3 tools/gen_flash_binaries.py`` adds the rest of the flash set
to that same folder. Chip directory names are lowercase.

``GET /api/firmware?mac=&cur_version=&chip=`` returns a JSON array. The device
identifies itself with ``chip`` (lowercase); the server lists only that chip's
firmware (defense in depth — the device also filters by ``targets`` locally).
``cur_version`` is optional and still served when omitted. ``mac`` is also
carried on the request. The array lists each application image:

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/firmware?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s -o minihub.bin "http://127.0.0.1:8080/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin?mac=aa:bb:cc:dd:ee:ff&cur_version=0.1.0"

.. code-block:: json

   [
     {
       "id": "esp32s31-0.1.0",
       "name": "minihub-esp32s31-0.1.0",
       "version": "0.1.0",
       "chip": "esp32s31",
       "targets": ["esp32s31"],
       "sha256": "0123abcd...",
       "size": 1234,
       "release_note": "first cut",
       "url": "/files/Firmwares/esp32s31/0.1.0/minihub-esp32s31-0.1.0.bin"
     }
   ]

* ``version`` — the version directory name.
* ``chip`` and ``targets`` — the chip directory name.
* ``sha256`` — the 64-digit hex digest of the ``.bin``.
* ``size`` — the byte length.
* ``release_note`` — the text of ``release_notes.txt`` in the same directory.
* ``url`` — a path inside the deploy root. When one version directory holds
  several application ``.bin`` files, ``id`` also includes the file name.

On the device, ``minihub_update_check()`` and ``minihub_update_apply()``:

1. Request the array above, with ``mac`` and ``version`` attached.
2. Keep the highest version whose ``targets`` match the local chip name
   (case-insensitive). A leading ``v`` on a version is ignored in the compare.
3. Download when that version is higher than ``CONFIG_MINIHUB_VERSION`` (or
   the application description version when that option is empty). The same
   version is downloaded again when its ``size`` or ``sha256`` differs from
   the last download record.
4. ``minihub_ota_start_url()`` opens ``url`` and attaches ``mac`` and ``version``. The download
   checks ``sha256`` against the 64-digit hex it computes, and discards a
   mismatch. The image is then written to the inactive OTA slot and the device
   reboots; see :doc:`../ota`.

Assets and web
--------------

``python3 tools/gen_deploy_index.py --deploy ROOT`` emits the device-type
registry from ``model/*.csv`` and ``images/*`` in the device-widget source:

* ``Assets/device_widgets.json`` — per ``device_id``: device icon + each
  parameter's icon/style/metadata URL.
* ``Assets/parameters.json`` — the global parameter registry
  (icon/style/metadata) keyed by parameter name.
* ``Assets/styles/<param>.css`` — one CSS file per parameter, extracted from
  ``parameters.csv`` ``css`` column.

The web and asset manifests (schema ``minihub.deploy.index/1``) are served
dynamically by ``store_server.py`` as ``GET /api/web`` and ``GET /api/assets``:
they are built from ``Webs/<version>/`` and ``Assets/`` at request time, so no
static ``index.json`` is written (mirroring ``GET /api/firmware``).

``--only assets`` rebuilds only the device-type registry after a single icon/style
file is dropped in — no firmware or plugin rebuild required. ``--sync-source``
copies ``model/`` and ``images/`` from the device-widget component into the
deploy root first.

.. code-block:: text

   ROOT/Assets/device_widgets.json
   ROOT/Assets/parameters.json
   ROOT/Assets/styles/<param>.css
   ROOT/Assets/model/*.csv
   ROOT/Assets/images/{devices,parameters}/*.svg
   ROOT/Webs/<version>/...   (manifest served at GET /api/web)

.. code-block:: bash

   curl -s "http://127.0.0.1:8080/api/assets?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s "http://127.0.0.1:8080/api/assets/device/light?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"
   curl -s "http://127.0.0.1:8080/api/web?mac=aa:bb:cc:dd:ee:ff&chip=esp32s31&cur_version=0.1.0"

On-demand device-type assets:

* ``GET /api/assets/device/<device_id>`` — that device's icon + each
  parameter's icon/style/metadata; 404 when unknown.
* ``GET /api/assets/parameter/<param>`` — the generic parameter entry.
* ``GET /files/...`` — serves the tree and rejects ``..`` / escape.

On the device, ``components/minihub_update`` reuses the HTTP client to fetch
``/api/assets/device/<id>`` when a type is unknown to the local registry,
caching icons under ``/data/images`` and styles under ``/data/styles``; the
rendering layer only reads local storage, so it stays decoupled.

``GET /files/...`` maps onto the deploy root and rejects a path that
contains ``..`` or escapes the root.

On the device, ``minihub_update_check()`` and ``minihub_update_apply()``
(``components/minihub_update``) read ``/api/firmware``,
``/api/assets``, and ``/api/web``. Firmware
calls ``minihub_ota_start_url()``. ``devices.csv`` and
``parameters.csv`` go through ``minihub_device_widget_put_model()`` into
``/data/config/model``. Other model files land in that directory.
Images land in ``/data/images``. Web files land in ``/data/web``.
Downloads are hashed while they are written; a mismatch is discarded.
