Pack and Catalog
================

:link_to_translation:`zh_CN:[中文]`

A Store module travels from a source folder on the developer PC to
``/store/modules/<id>/`` on the Hub.

Prerequisites
-------------

* L1 / L2 packing does not require a Host firmware build
* The Hub running L2 must also have been flashed with
  ``CONFIG_MINIHUB_DYNAMIC_MODULES``
* ``pip install pyyaml`` at the repo root if scripts fail on PyYAML
* Optional: ``export MINIHUB_PLUGINS_DEPLOY_DIR=~/workspace/minihub_store``

.. only:: not hide_l3

   * L3 **out-of-tree** cross-compile: an MHMD ``.so`` is enough (see
     :doc:`develop_l3`); no firmware build
   * L3 **in-tree** with the Host: the product must enable
     ``CONFIG_MINIHUB_DYNAMIC_MODULES`` (``dynamic_modules`` in ``app.yml``),
     or CMake will not emit ``libadapter_*.so``
   * The Hub **running** L3 must also have been flashed with that option

Pack commands
-------------

.. code-block:: bash

   # Any tier by id.
   python3 tools/pack_store_module.py pack ID
   python3 tools/pack_store_module.py pack all

   # After .mhub files are in the store directory, rewrite catalog.json.
   # Default: walk Stores/<bucket>/ID/ID.mhub (L1/L2 live under Stores/Common).
   python3 tools/sync_store_catalog.py
   python3 tools/sync_store_catalog.py --deploy ~/workspace/minihub_store

   # Pack from plugin sources, then rewrite catalog the same way
   python3 tools/sync_store_catalog.py all
   python3 tools/store_server.py

.. only:: not hide_l3

   .. code-block:: bash

      # Compile every in-tree native plugin and pack its .mhub
      ./tools/build_firmware.py -app minihub modules

      # One native plugin
      ./tools/build_firmware.py -app minihub module ID

      # Pack only when in-tree .so already exists (does not compile C)
      ./tools/build_firmware.py -app minihub pack

      # Manual MHMD wrap (usually done inside pack / standalone CMake)
      python3 tools/pack_store_module.py mhmd in.so out.so

      # No-IDF build for an L3 module (no in-tree demo; scaffold one first)
      python3 tools/build_plugin_standalone.py my_native

   ``./tools/build_firmware.py … modules`` compiles every native plugin that has
   both ``module.json`` and ``CMakeLists.txt`` (``examples/plugins/*/``
   plus ``MINIHUB_PLUGIN_DIRS``) and wraps each MHMD ``.so`` in the build tree.
   That compile does not create a store plugin folder. A Host firmware
   ``build`` does not compile those plugins. ``./tools/build_firmware.py …
   pack ID`` wraps an existing ``libadapter_ID.so`` into a local MHMD ``.so``
   and does not write ``Stores/Common/ID/`` or ``Stores/<chip>/``.

After the ``.mhub`` files are already in the store directory (for example
``~/workspace/minihub_store/Stores/Common/ble_mesh_pack/ble_mesh_pack.mhub``), run
``sync_store_catalog.py`` (``--from-store`` is the default). It walks each
``Stores/Common/ID/ID.mhub``, reads ``module.json``, and writes ``catalog.json``
beside that package. ``ui`` and ``capabilities`` stay in the package
``meta.json``.
Plugin sources are not required.
``GET /api/catalog`` aggregates those objects;
copying a zip alone does not update the catalog. Default deploy root is
``MINIHUB_PLUGINS_DEPLOY_DIR`` or ``~/workspace/minihub_store``.

.. only:: not hide_l3

   The same script is inside ``module_sdk.zip``.

Deploy layout
-------------

.. code-block:: text

   DEPLOY/Stores/Common/ID/catalog.json
   DEPLOY/Stores/Common/ID/ID.mhub

Default ``store_server.py`` listen address: ``http://0.0.0.0:8080``
(override with ``--port``).

Outer container format: **zip** (``MHUB_PACK_FORMAT``, default ``zip``). Host
unpacker: ``components/minihub_store/hub_zip.c`` (zip only today).

.. only:: not hide_l3

   **MHMD** is the inner native image magic (``0x4D484D44``), not the outer zip name.

``catalog.json`` entry (generated by ``sync_store_catalog.py``)
-----------------------------------------------------------------

.. code-block:: json

   {
     "type": "module",
     "id": "color_bulb_js",
     "name": "Color Bulb (JS)",
     "version": "0.1.0",
     "targets": ["ALL"],
     "url": "/files/Stores/Common/color_bulb_js/color_bulb_js.mhub",
     "adapter": "color_bulb_js",
     "size": 3762
   }

* ``type`` — always ``module`` in a generated catalog. What marks an L1 config
  pack is ``config_only: true`` (a ``.json`` install URL works too);
  ``runtime: "pack"`` is written alongside and is what the package classifier
  and the loader use to route the package to ``minihub_pack`` rather than
  treat it as a loadable module. A hand-written ``"type": "pack"`` is honoured
  only where the Hub reports installed state — it cannot be *installed*: the
  catalog lookup lets a ``pack`` request find a ``module`` entry (and the
  reverse) only for ``config_only`` items, and an entry whose ``url`` ends in
  ``.mhub`` is not one of those (``minihub_store.c:999-1006,1027-1036``).
* ``url`` — path or absolute HTTP URL of the ``.mhub``
* ``targets`` — lowercase chip folder names, the same strings as the firmware
  directories (for example ``esp32s31``), or ``ALL`` for a JS module. Copied
  from ``module.json``. A concrete chip is lowercased; ``ALL`` stays ``ALL``.
  When the field is omitted, pack writes ``["ALL"]`` for a JS module and
  ``["esp32s31"]`` for every other module
* ``adapter`` — optional; Host creates an ``adapters.json`` slot on install
* ``size`` — **outer zip** byte length (must match the ``.mhub`` on disk;
  ``pack`` rewrites this)

* ``binary_size`` — the inner native image size, not the zip. It is stamped from
  that id's compiled image whenever the packer finds one under the app build
  directory, so a non-zero ``binary_size`` next to a ``runtime: js`` entry means
  a leftover artifact from an earlier build of the same id, not a native module
  (``sync_store_catalog.py:258-266``).
* ``sha256`` — the packer hashes every package and writes it here, and the
  Store API echoes it, but the install path never verifies it: ``size`` must
  match, the digest is not checked. Digest verification exists only for the
  firmware and asset records in ``components/minihub_update/``.

``type`` means different things in the two files: a generated ``catalog.json``
says ``module`` for every tier, while the ``module.json`` inside an L1 package
says ``pack``.

Install on a running Hub
------------------------

**From local Store server** (Web UI → Store → refresh catalog → install).

**Web UI** — open ``http://HUB/`` and go to **Store**, set the custom Store URL
to your local server, refresh the catalog, then install ``color_bulb_js``. The
Hub reloads the module automatically after install.

L1 packs appear as a pack entry in the Store UI.

Verify installation
-------------------

.. note::

   ``$HUB`` is the device's LAN address. With Web login on (the default), log in
   once and reuse the cookie:

   .. code-block:: bash

      export HUB=<hub-ip>          # from the eth got IP log line
      curl -s -c /tmp/mh -X POST http://$HUB/api/auth/login \
        -H 'Content-Type: application/json' \
        -d '{"username":"admin","password":"secret1"}'

.. code-block:: bash

   curl -s -b /tmp/mh http://$HUB/api/modules
   curl -s -b /tmp/mh http://$HUB/api/packs
   curl -s -b /tmp/mh http://$HUB/api/config/adapters

Serial log: a JS module reports ``JS module '<id>' setup ok``; a native module
reports ``loaded module binary: <path>``.

Upgrade / uninstall
-------------------

Upgrade:

.. code-block:: bash

   curl -s -b /tmp/mh -X POST http://$HUB/api/store/upgrade \
     -H 'Content-Type: application/json' \
     -d '{"type":"module","id":"color_bulb_js"}'

Uninstall:

.. code-block:: bash

   curl -s -b /tmp/mh -X POST http://$HUB/api/store/uninstall \
     -H 'Content-Type: application/json' \
     -d '{"type":"module","id":"color_bulb_js"}'
